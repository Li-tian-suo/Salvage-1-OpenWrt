## 三、你上次发现的问题，现在什么状态

### Wi-Fi 完全起不来 → **已修复并验证**

在板子上手动补 cal 文件后重启，Wi-Fi 立刻恢复：

```
phy0-ap0  ch36 (5180 MHz)  80 MHz  23 dBm   ← 5G
phy1-ap0  ch1  (2412 MHz)  20 MHz  20 dBm   ← 2.4G
```

新固件里已包含这个修复，刷进去不需要手动补。

### 跑 homebox 就 Wi-Fi 去世 → **已加自愈，根因待确认**

**已确认的事实**：

```
ping 192.168.1.1     通
:80  LuCI            通
:22  ssh             通
:3300 homebox        通
Windows 扫描 SSID     完全搜不到
```

系统活着，只有无线死了，重启就恢复。

**已排除**：不是 OOM（20 MB / 884 MB）、不是 homebox 自身、
不是 CPU（load 0.11）。

**强怀疑**：NSS 的 WLAN 数据面 offload（`qcom,wlan-dataplane-offload-enabled`）。
Wi-Fi 的帧处理跑在 NSS 固件里，NSS 一崩 Wi-Fi 就静默消失，CPU 和以太网不受影响。
但这来自上游公共 dtsi，全部 37 个 ipq807x 设备都用，
所以不是我们移植引入的。

**当前的应对**：`hk09-wifiguard` 每 20 秒查一次 `iw dev`，
接口少了就 `wifi reload`，再不行 `wifi down/up`，连续 3 次失败就停手记日志。
**它不会自动重启整机**（那会连有线一起断，还会冲掉崩溃现场）。

**下一步要做的**：刷新固件后，再跑一次 homebox，然后如果有问题就看

```sh
cat /sys/fs/pstore/dmesg-ramoops-0     # 崩溃现场（新固件才有）
dmesg | grep -iE 'nss|ath11k' | tail -40
logread | grep hk09-wifiguard          # 看门狗做了什么
```

pstore 打开之后，下次崩溃就能抓到真正的调用栈了。

导致 Run #5 直接失败、白白浪费时间。

```sh
git cat-file -p <commit>:<path> | wc -c
```

对比历史大小，差太多就是搞错了文件。
