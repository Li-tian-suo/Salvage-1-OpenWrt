## 一、这是什么

有人在 `ccmx200/Salvage-1-OpenWrt` 上做了部分适配（上游参考设备叫 `Salvage-1`），
我接着把它推到**能编、能刷、能跑**的状态，并且解决上板后才暴露的几个真 bug。

一句话结论：**固件能编出来了，Wi-Fi 也修好了，还有两个遗留问题在查**
（高负载后 Wi-Fi 消失 / 有线无线都偏慢）。

### 网口映射（注意：**与丝印相反**）

本板 DTS 用 `&dpN` 标签改写，节点地址定义在上游 `ipq8074-ess.dtsi` 里。
下表「标签」列是 DTS 里的写法，「上游节点」列是展开后的地址。

| 标签 | 上游节点 | 丝印 | PHY | 速率 |
|---|---|---|---|---|
| `&dp1` | `dp1@3a001000` | lan3 | QCA8075-0 | 1G |
| `&dp2` | `dp2@3a001200` | lan2 | QCA8075-1 | 1G |
| `&dp3` | `dp3@3a001400` | lan1 | QCA8075-2 | 1G |
| `&dp5` | `dp5@3a001800` | wan | QCA8081 | **2.5G** |

对应的 DTS 片段：

```dts
&dp1 { phy-mode = "qsgmii"; phy-handle = <&qca8075_0>; label = "lan3"; };
&dp2 { phy-mode = "qsgmii"; phy-handle = <&qca8075_1>; label = "lan2"; };
&dp3 { phy-mode = "qsgmii"; phy-handle = <&qca8075_2>; label = "lan1"; };
&dp5 { phy-mode = "sgmii";  phy-handle = <&qca8081>;   label = "wan";  };
```

`aliases` 里也按这个顺序登记：

```dts
ethernet0 = &dp5;   /* 2.5G WAN (QCA8081) */
ethernet1 = &dp3;
ethernet2 = &dp2;
ethernet3 = &dp1;
```

掉线排查时最容易踩的坑：**插 lan1 口，系统里看到的是 `dp3`**。

### 交换机 / PHY

```dts
switch_lan_bmp   = 0x0e   /* PORT1 | PORT2 | PORT3 */
switch_wan_bmp   = 0x20   /* PORT5 */
switch_mac_mode  = 0x0b   /* QSGMII */
switch_mac_mode1 = 0x0c   /* SGMII_PLUS */
switch_mac_mode2 = 0xff   /* DISABLED */
```

PHY ID：QCA8081 = `0x004d.d101`，QCA8075 = `0x4d / 0xd0b1`。
U-Boot 里能直接看到这两组 ID，可作为硬件在位验证。

### 3.4 无线看门狗（`hk09-wifiguard`）

解决“跑 homebox 就 Wi-Fi 去世”的自愈问题。

三个文件：

```
files/usr/bin/hk09-wifiguard              主程序（看门狗状态机）
files/etc/init.d/hk09-wifiguard           procd 服务
files/etc/uci-defaults/97-hk09-wifiguard  首次启动自动 enable
```

策略（由轻到重）：

1. 每 20 秒 `iw dev` 数接口，够数就什么都不做
2. 少了 → `wifi reload`
3. 还不行 → `wifi down; wifi up`
4. 连续 3 次失败 → 记 error 日志后停手

**故意不自动重启整机**：那会连有线一起断，还会把崩溃现场冲掉。

## 四、踩过的坑（按严重程度排序）

这一节是整份文档最有价值的部分。**每一条都是实际踩到、有日志证据的。**

### 坑 1（致命）：CAL data 不生成 → Wi-Fi 两个频段全挂

**现象**：以太网完全正常，LuCI 能开，但 `iw dev` 空，
`wifi status` 里 `retry_setup_failed: true`。

**上游报错很有迷惑性**：

```
netifd: radio1: wifi-scripts: Bug: PHY is undefined for device
```

看起来像 LuCI 的 wifi-scripts 有 bug，其实不是。

**真正原因**在 `dmesg` 里：

```
ath11k c000000.wifi: qmi failed to load CAL data file:cal-ahb-c000000.wifi.bin
ath11k c000000.wifi: failed to load board data file: -12
```

`/lib/firmware/ath11k/IPQ8074/hw2.0/` 只有 `board-2.bin`，没有 `cal-*.bin`。

**根因**：`11-ath11k-caldata` 按 `board_name` 分支，
上游只有 `cuicanmx,salvage-1)`，我们的是 `hk09,hk09`，
匹配不上 → 落到 `*)` → `exit 1` → cal 文件不生成。

**修复**：`diy-part2.sh` 第 0 步给脚本加 `hk09,hk09)` 分支。

**验证**：在板子上手动 `dd` 出 cal 文件再重启，Wi-Fi 立刻恢复：

```
phy0-ap0  ch36 (5180 MHz)  80 MHz  23 dBm    ← 5G
phy1-ap0  ch1  (2412 MHz)  20 MHz  20 dBm    ← 2.4G
```

**可复现的手工提取命令**（应急用）：

```sh
dd if=/dev/mtd18 of=/lib/firmware/ath11k/IPQ8074/hw2.0/cal-ahb-c000000.wifi.bin \
   bs=4096 skip=1 count=32
```

即取 ART 的 `0x1000` 起、128 KiB。

### 坑 2：按键和 NAND 抢 GPIO12

**现象**：

```
ipq8074-pinctrl 1000000.pinctrl: pin GPIO_12 already requested by 79b0000.nand-controller;
                                   cannot claim for gpio_keys
gpio-keys gpio_keys: Error applying setting, reverse things back
```

**原因**：`button_pins` 里写 `pins = "gpio12"`，但 `gpio_keys` 用的是 `&tlmm 34`。
DTS 里那条注释其实早就写了「我最初把 phandle 0x0c 当成 GPIO 12，是误读」，
但**代码一直没跟着改**。

**修复**：`pins` 改 `gpio34`，`bias-pull-down` 改 `bias-pull-up`。

### 坑 3：`diy-part2.sh` 被自己的模板覆盖，构建直接失败

**这是我自己造的回归，值得单独记一条。**

本地 `buildrepo/diy-part2.sh` 其实只是个转发模板：

```sh
source "$GITHUB_WORKSPACE/hk09/build/diy-part2.sh"
```

而仓库里**没有** `hk09/` 目录。真正的注入脚本一直就是仓库根目录的
`diy-part2.sh` 本体（自包含）。

我把本地模板覆盖上去之后，Run #5 精准地死在
`载入配置并注入设备（diy-part2.sh）`，后续步骤全部 skip。

**教训**：覆盖远程文件之前，先确认**哪个文件才是真身**。
可以 `git cat-file -p <commit>:<path> | wc -c` 对比历史大小。

### 坑 4：`.gitignore` 的 `bin/` 把 `files/usr/bin/` 一起吃了

`.gitignore` 里写 `bin/`，git 会匹配**任意层级**的 bin 目录。
结果 `files/usr/bin/hk09-wifiguard` 被静默忽略，
提交里只有 init.d 和 uci-defaults 两个文件，主程序根本没进去。

后果很隐蔽：固件能编出来，但 `/usr/bin/hk09-wifiguard` 不存在，
init 脚本指向空文件，服务无限 respawn 失败。

**修复**：所有目录规则加前导 `/`（`/bin/` `/dl/` ...），只匹配仓库根。

```sh
git check-ignore -v files/usr/bin/hk09-wifiguard
# 会直接告诉你是哪条规则匹配的
```

### 坑 5：`CONFIG_KERNEL_PSTORE=y` 是无效写法

想让崩溃日志留下，我先往 `.config` 加了：

```ini
CONFIG_KERNEL_PSTORE=y
CONFIG_KERNEL_PSTORE_RAM=y
CONFIG_KERNEL_PANIC_TIMEOUT=30
```

跑 `make defconfig` 之后，**这 6 行全部消失**（连 `is not set` 都不留）。

**原因**：`CONFIG_KERNEL_*` 只在 `config/Config-kernel.in` 的 218 个条目里有效
（如 `KERNEL_DEVMEM`）。全树 `grep 'config KERNEL_PSTORE'` 零命中。

**正确做法**：直接改 `target/linux/qualcommax/config-6.12`，
或在 `diy-part2.sh` 里追加。已按这个方式实现并本地验证 8/8 PASS。

### 坑 6：WSL 里 `git push` 的代理陷阱

`/etc/profile.d/99-proxy.sh` 只在**交互式** shell 生效。
`wsl -- bash script.sh` 是非交互的，不 source 它，git 实际在直连，
于是报：

```
GnuTLS recv error (-110): The TLS connection was non-properly terminated.
```

**解法**：自己算网关，显式给 git 传代理：

```sh
_gw=$(awk '$2 == "00000000" {print $3; exit}' /proc/net/route)
HOST="$((16#${_gw:6:2})).$((16#${_gw:4:2})).$((16#${_gw:2:2})).$((16#${_gw:0:2}))"
git -c http.proxy="http://$HOST:7891" push ...
```

### 坑 7：串口脚本发 Ctrl-C 把登录 shell 打死

早先的串口脚本习惯先发 `\x03`（Ctrl-C）清屏。
在 OpenWrt 上这会丢弃登录 shell，表现为：

```
^CPlease press Enter to activate this console.
```

反复出现，看起来像「串口完全没反应」。

**修复**：只发换行符，绝不发 Ctrl-C。

### 坑 8：U-Boot 吞字符

串口一次性写入 `run bootcmd`，U-Boot 会收成 `un bootcmd`。

**修复**：逐字符发送，每个字符间隔 8 ms。

### 5.3 刷机约束（重要）

板子当前 `rootfs` UBI 卷只有 **182 LEB = 23,109,632 B ≈ 22 MiB**，
而 Run #8 的 `factory.ubi` 是 **40,239,104 B**，需要约 **317 LEB**。
`available LEBs = 0`。

所以**必须**先腾空间：

```sh
ubi remove rootfs
ubi remove rootfs_data
ubi create rootfs $filesize
ubi write 0x44000000 rootfs $filesize
```

**绝不能碰** `mtd18`（`0:ART`）和 `mtd15`（`0:APPSBLENV`）。

**首选方案**：先 `tftpboot` 加载 initramfs 起来测试，**不写 flash**：

```
tftpboot 0x44000000 <initramfs-uImage.itb>
bootm 0x44000000
```

### 5.4 U-Boot 备忘

```
bootcmd=ubi part rootfs; ubi read 0x44000000 kernel; bootm 0x44000000
```

- **没有 `boot` 命令**，用 `run bootcmd`
- 进 U-Boot：启动时按任意键
- FIT 配置名是 **`config@hk01`**（不是 `hk09`，这点容易搞错）

## 六、Wi-Fi：160 MHz 与功率

### 6.1 160 MHz 为什么显示 80

不是 bug，是**监管域限制**：

| 国家码 | 5G 可用带宽 |
|---|---|
| CN | DFS-FCC → 5150-5350 @ 160 MHz |
| AU | DFS-ETSI → 5150-5250 @ **80 MHz**（静默砍到 80） |

LuCI 只显示 UCI 里的值，不反映实际生效的带宽，所以会看到「设了 160 显示 80」。

**CN 下开 160 MHz 会强制用 DFS 信道 52–64**，每次 `wifi up` 后要等
**约 60 秒 CAC**（信道可用性检查）。这期间：

```
Channel: 0 (unknown GHz)
Cannot set beacons during CCA period
```

都是**正常现象**，不是坏了。

想立刻可用又不漂移，就用非 DFS 的 36/40/44/48，无需 CAC。

### 6.2 功率上限

`txpower` 的上限来自监管域，**不是 BDF 限制**：

| 国家码 | 5G 上限 |
|---|---|
| US | 30 dBm |
| JP | 23 dBm |
| CN | 20 dBm |

实测本板 5G 跑在 23 dBm、2.4G 20 dBm，已经在合理范围。
「解锁功率」这件事在合规层面没有正当做法，能改的只是国家码。

## 七、LuCI 慢的原因（已定位）

实测数据：

| 指标 | 值 |
|---|---|
| ping | 0 ms |
| TCP :80 建连 | 1 ms |
| load | 0.04 |
| RAM | 244 / 884 MB |
| 首次 LuCI 请求 | **5295 ms** |
| 后续请求 | 68 / 115 / 684 ms |
| 10 个静态资源 | 575 KB / 1783 ms |

**根因**：`uhttpd` 默认 `max_requests=3`，浏览器并发拉资源时全部排队；
且**不支持 gzip**，JS/CSS 全部原样传输。

**已做**：`files/etc/uci-defaults/98-hk09-perf` 里设
`max_requests=20`、`max_connections=200`。

## 八、分区：不建议合并

有人问过能不能把空闲分区合并。**结论：不要动。**

看起来全空的那几个（`0:DEVCFG_1`、`0:APDP`、`0:APDP_1`、`0:RPM_1`、
`0:CDT_1`、`0:ETHPHYFW`）是 **Qualcomm 双启动备份槽**，不是垃圾。

而且 `mtd4` 有 336 字节非 FF 数据，`mtd6`（`0:QSEE_1`）有 682,762 字节。
合并会破坏双启动能力，风险远大于收益。

**ART 校验值**（改机前先备份）：

```
dd if=/dev/mtd18 bs=1024 skip=4 count=128 | md5sum
702471f9b273dec6ffc16d88ccebeb27
```

## 九、遗留问题

### 9.1 高负载后 Wi-Fi 消失（部分解决）

**现象**：跑 homebox 测速打满带宽后，Wi-Fi 整体消失。

**⚠️ 一处必须更正的判断**

早期我写下过这样的「事实」：

```
ping 192.168.1.1     通
:80  LuCI            通
:22  ssh             通
:3300 homebox        通
Windows 扫描 SSID     完全没有
```

并据此认为「**系统存活，只有无线死了**」。

**这个推论是错的。** 后来查 MAC 才发现：

```
68:de:ce:67:55:60  →  Fiberhome（烽火通信）
ttyd :7681 显示     →  ponwrt login:
```

**`192.168.1.1` 是一台烽火光猫，不是 HK09 板子。**

也就是说那组「全通」的数据说明的是光猫的状态，跟板子无关；
「扫描不到 SSID」也不能证明是板子的 Wi-Fi 挂了，因为板子可能根本没通电。

**正确的结论应该是**：这个现象的**根因至今未确认**，
需要等板子真正连上、能读到 `dmesg` 之后再判断。

**曾经排除过的**（这些是在真的板子上测的，仍然有效）：

- 不是 OOM：板子上 homebox 只占 20 MB，空闲 600+ MB
- 不是 homebox 自身：本地访问 44 ms，init 脚本不碰网络
- 不是 CPU：load 0.11

**强怀疑（未验证）**：NSS 的 WLAN 数据面 offload。

DTS 里 `ipq8072-hk09.dts` include 了 `ipq8074-nss.dtsi`，其中：

```dts
qcom,wlan-dataplane-offload-enabled;    /* Wi-Fi 数据面交给 NSS */
qcom,ppe-enabled;
```

Wi-Fi 的帧处理跑在 NSS 固件里，NSS 一崩，Wi-Fi 就静默消失，
而 CPU 和以太网完全不受影响。

但注意：`ipq8074-nss.dtsi` 被**全部 37 个 ipq807x 设备**引用
（包括上游原版 salvage-1），所以这不是本移植引入的。

**当前缓解**：`hk09-wifiguard` 看门狗自动 `wifi reload` / `down-up`。

**待办**：板子连上后读 `dmesg | grep -i ath11k`，
并复现一次高负载，看 `/sys/fs/pstore/` 有没有崩溃现场
（ramoops 已在固件里打开，验证见 `17-firmware-verified.md`）。


### 9.2 有线也偏慢

现象是「网线和 wifi 都慢」。有线侧还没单独量化。
可能和 NSS offload / SQM 配置有关，需要 `iperf3` 分层测（先内网后外网）。

### 9.3 ART 里 MAC 无效

```
eth0 MAC Address from ART is not valid
```

导致每次启动随机 MAC，且 lan1 和 wan 可能撞成同一个。
这是板子出厂就有的问题，不影响功能。

## 十二、给下一个接手的人

1. **先读 `docs/13-onboard-bugs.md`**，那里有完整的 bug 定位过程。
2. **改任何配置后跑 `make defconfig`**，检查包没被静默丢弃。
3. **覆盖远程文件前先确认哪个是真身**（`git cat-file -p <commit>:<path> | wc -c`）。
4. **首次刷机用 initramfs**，不写 flash。
5. **串口绝不发 Ctrl-C**。
6. **`board_name` 是本移植的命门** —— 凡是在上游按 `cuicanmx,salvage-1`
   分支的地方，都要检查有没有 `hk09,hk09` 分支。
7. **别猜，去板子上看 `dmesg`**。我在这上面浪费了不少时间。
